# 发布与验收失败修复回流

## 统一入口

```text
/skill YunxiaoQA
接收发布回流：发版任务=TASK-900；触发=发布失败|产品验收失败；证据=ID或URL
```

按发版任务精确读取生产事件区块或产品验收不通过区块、受影响需求、原测试任务、迭代、当前版本和回滚结果。只接受正式`发布失败`，或仍为`发布完成`但存在可解析的产品验收不通过证据；聊天转述不能启动回流。

1. 生成`回流批次ID=发版任务+失败证据+受影响范围`，写入原测试任务的受管回流区块并回读，不修改已经完成的测试任务状态。
2. 为每个可独立修复的问题创建或复用正式Bug，关联原测试任务，在描述中记录发版任务、回流批次、失败现象、影响范围、生产/回滚证据和复现路径。
3. 每个Bug仍由当前测试用户担任验证者，负责人按代码归属解析；输出逐Bug开发口令：

```text
/skill yunxiao-development-delivery
修复bug:<BUG-ID>
```

## 修复后验证

```text
/skill YunxiaoQA
验证发布回流：发版任务=TASK-900；缺陷=ONEOS-a,ONEOS-b；回归证据清单=<JSON文件>
```

必须同时满足：

- 回流批次与发版任务、迭代、需求范围一致；
- 开发修复已统一部署到test，部署执行ID、版本和证据可读；
- 每个Bug均按原失败路径复测并写入独立`oneos.bug-retest/v1`证据后关闭；
- 回归证据清单可核验，未执行/失败/阻塞均为0；
- 所有暂不修复项具有新的回流批准证据，不复用原发布批准。

通过后在原测试任务写入`oneos.release-repair-qa/v1`区块并回读，输出：

```text
/skill yunxiao-release-operations
重新发布：发版任务=TASK-900；回归证据=<证据ID或URL>
```

不得直接再次产品验收，不得绕过修复后的test部署与逐Bug复测。
