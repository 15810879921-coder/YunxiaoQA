# 口令面

```text
拉取测试任务：状态=待处理|处理中；[项目=…]
开始测试：测试任务=ONEOS-xx；[需求=ONEOS-yy]
记录历史测试证据（可选）：测试任务=ONEOS-xx；证据清单=<JSON文件>
发起缺陷：标题=…；描述=…；[测试任务=ONEOS-xx | 交付=ONEOS-xx]；[负责人=…]；[证据=…]
从测试用例发起缺陷：测试用例=CASE-xx；标题=…；描述=…；[测试任务=ONEOS-xx]；[负责人=…]；[证据=…]
发起缺陷(非本期)：标题=…；描述=…；负责人=…；[项目=…]
拉取待验缺陷：状态=已修复|暂不修复；[测试任务=…]；[负责人=…]
批量关闭已修复：缺陷=ONEOS-a；复测用例=CASE-ID；复测执行=RUN-ID；test版本=VERSION；证据=ID或URL；验证人=当前用户
再次打开：缺陷=ONEOS-xx；[原因=复现说明]；[证据=…]
并入当期迭代：缺陷=… 或 范围=已关闭且未挂迭代；迭代=（当期/指定名）
完成测试：测试任务=ONEOS-xx；[需求=ONEOS-yy]；测试计划=<TestHub计划ID>；[暂不修复批准=BUG-ID:批准人|证据]
人工验证通过并完成：测试任务=ONEOS-xx；[需求=ONEOS-yy]
需求测试完成：测试任务=ONEOS-xx；[需求=ONEOS-yy]
接收发布回流：发版任务=TASK-900；触发=发布失败|产品验收失败；证据=ID或URL
验证发布回流：发版任务=TASK-900；缺陷=ONEOS-a,ONEOS-b；回归证据清单=<JSON文件>
闭环测试任务：测试任务=ONEOS-xx（兼容口令；按“完成测试”完整门禁执行）
```

## 条线映射

| 条线 | 口令 |
|---|---|
| 1·A 知悉提测 | `拉取测试任务` + `开始测试` |
| 1·B 测出 bug | `发起缺陷`或`从测试用例发起缺陷`（绑测试任务/交付） |
| 1·C 测试完成 | `记录测试证据` + `完成测试` |
| 1·C 人工快捷闭环 | `人工验证通过并完成`（明确人工通过；不产出发布候选） |
| 1·C′ 无缺陷回写需求 | `需求测试完成`（【测试】已完成+验证通过+无缺陷单） |
| 2·1 非本期 bug | `发起缺陷(非本期)` |
| 2·3 回归闭环 | `拉取待验缺陷` + `批量关闭已修复` + `再次打开` + `并入当期迭代` |

## UI 多账号验收（测试环境）

多角色/多用户 UI 验收时，**切账号**按 [test-env-account-switch.md](test-env-account-switch.md)：退出 → 登录目标用户名，密码统一 `admin123`；同账号多角色用「切换角色」。缺陷证据只写用户名/花名，不写密码。

## 口令细则

### 拉取测试任务

- 默认状态：`待处理` + `处理中`。
- 回报：编号、标题、状态、所属【交付】、计划开始、优先级/标签（若有）。
- 只读；可不进 Plan。

### 发起缺陷（本期）

- 必填：标题、描述；`测试任务=` 可口令给出，**未给出或非唯一命中则挂载点选**。
- **挂载点选**：`list_bug_anchors.py` → AskQuestion 点选【测试】；需求可选点选写入描述追溯。见 [anchor-selection.md](anchor-selection.md)。
- **关联规则**：
  1. 缺陷 `ASSOCIATED` 关联该【测试】编号（关联项，非父子）——硬门禁；
  2. 产品需求写入描述「追溯需求」；**不做** ASSOCIATED API（本期）。
- 验证者：当前登录测试用户。由共同建单处理器根据云效新建记录中的当前会话用户写入并回读，禁止口令覆盖。
- 负责人：同交付下【开发】任务负责人；多条 → Plan 点选；口令 `负责人=` 优先。
- 必须走 SKILL「发起缺陷流水线」+ `create_bug.py`。

### 发起缺陷(非本期)

- 必填：标题、描述、`负责人=`。
- 默认仍走挂载点选（【测试】+需求）；仅当 Plan 明确「无测试锚点」才允许 `--allow-no-test`。
- 验证者强制为当前登录测试用户；不可口令覆盖。
- 同样强制诊断流水线。

### 从测试用例发起缺陷

- 必填：`测试用例=`、标题、描述；其余锚点、负责人和关系门禁与本期`发起缺陷`一致。
- 调用共同处理器：`create_bug.py --source test-case --test-case <用例编号/执行记录>`。
- 测试用例来源写入缺陷描述作追溯；没有已验证的正式关系时不得伪造关联成功。
- 验证者规则与独立建单完全相同：只允许当前登录测试用户，写入后回读。

### 拉取待验缺陷

- 默认状态：`已修复` + `暂不修复`。
- 可按测试任务 / 负责人过滤。
- 只读；可不进 Plan。

### 状态名注意（01_ONEOS）

- 缺陷「新建/打开」统一写 **待确认**（id=`28`）；**禁止**用「待处理」指缺陷。
- 「待处理」仅用于【测试】等**任务**（id=`100005`）。
- 「暂不修复」实网存在（id=`31`）；工作流可从待确认/再次打开迁入。

### 批量关闭已修复

- 仅处理状态=`已修复` 的缺陷 → `已关闭`。
- 每条Bug分别提供复测用例ID、复测执行ID、test环境已部署版本、证据ID/URL和当前验证人；调用`transit_bug.py`逐条写入并回读`oneos.bug-retest/v1`区块后才允许关闭。
- **小程序**交付无test流水线：复测版本填小程序测试版本标识（非空），部署证据文件写`deliveryEnd=小程序`+`testPipeline=skipped`，不要求执行ID与流水线部署版本；仍要求逐Bug复测用例、执行记录和证据。
- 批量口令只是冻结队列并逐条调用同一门禁，禁止用一份“整体回归通过”证据关闭多个Bug。
- **跳过**缺证据、复测失败、口头确认、仍复现或已执行`再次打开`的单。
- 写操作 → 必须 Plan。

### 再次打开

- 仅允许：当前状态=`已修复` → `再次打开`。
- 触发：回归时原路径仍复现。
- 必填复现说明（`原因=` 或描述追加「复测记录」）；有证据则附上。
- 负责人、验证者默认不改。
- 对 `待确认`/`再次打开`：禁止重复打开。
- 对 `暂不修复`：默认拒绝；用户在 Plan 显式确认「坚持再次打开」才可。
- 写操作 → 必须 Plan。

### 并入当期迭代

- 仅 `已关闭` 缺陷。
- `迭代=` 当期（按项目默认前缀下进行中迭代）或指定名称；**禁止本 Skill 创建迭代**。
- 迭代按端分列（`Web` / `小程序`）：目标迭代端别必须与缺陷来源【交付】端侧标签一致；端别无法唯一判定时停下问，不跨端并入。
- 写操作 → 必须 Plan。

### 开始、记录证据与完成测试

- `开始测试`同时推进【测试】`待处理→处理中`和需求`待测试→测试中`。
- `记录历史测试证据`是可选兼容动作：使用`yunxiao_cli_test_lifecycle.py record --evidence-manifest ...`幂等写入并回读，不推进状态，也不构成完成测试前置条件。
- `完成测试`必须传`--test-plan-id`，由脚本直接回读 TestHub 计划进度；不接受聊天自报用例计数。
- `完成测试`须校验正式关系、父【交付】迭代、当前计划用例总数大于0且未执行/失败/阻塞均为0、逐Bug复测记录与暂不修复批准，同时推进【测试】`处理中→已完成`和需求`测试中→测试完成`。
- 不要求test环境部署成功记录、部署执行ID/实际版本、正式测试报告ID/链接或`oneos.qa-evidence/v1`清单/哈希；历史资料存在时可保留，但不得作为开始或完成测试门禁。
- **唯一完整入口**：`skill-run yunxiao_cli_test_lifecycle.py start|record|complete ...`（先预检，确认后加`--apply`；启动规则见 [runtime-launcher.md](runtime-launcher.md)）。
- 旧`close_test_task.py`仅保留为拒绝式兼容入口，固定不写状态并返回完整`complete --test-plan-id`命令；不得用于正式闭环。
- 完整参数、证据区块和发布交接见 [test-execution.md](test-execution.md)。
- 回报必须含两侧`serialNumber | subject | from→to`；任一回读不符则停。
- **禁止**浏览器点状态菜单 / 可交互节点。
- 写操作 → 必须 Plan。

### 需求测试完成（无缺陷捷径）

- **口径：** 测试任务完成并且验证通过的（无缺陷单），把需求单状态改为测试完成。
- 前置：【测试】=`已完成`；验证结论通过（评论或用户确认）；关联缺陷无`待确认/处理中/已修复/再次打开`。
- 动作：需求`测试中→测试完成`；编号硬门禁 + 回读。
- **脚本**：`skill-run yunxiao_cli_req_test_complete.py --space-id <项目ID> --test-sn ONEOS-xx [--req-sn ONEOS-yy] [--test-plan-id <计划ID>]`；确认后加 `--apply`。
- 与完整`完成测试`并列：本口令**不**代替 TestHub 计划结果和缺陷闭环门禁；用于任务已完成且无缺陷时单独回写需求。
- 写操作 → 必须 Plan。

### 人工验证通过并完成

- 用户须针对明确测试任务编号确认人工验证通过；泛化的“继续”不能触发。
- 使用`yunxiao_cli_test_lifecycle.py manual-complete --manual-verdict passed`，先预检、Plan确认后加`--apply`。
- 仍校验唯一父【交付】、唯一正式关联需求、允许的源状态和无活动缺陷。
- 不要求部署证据、TestHub或QA manifest；按需补齐中间态，最终【测试】=`已完成`、需求=`测试完成`并逐步回读。
- 回执必须标记`evidenceMode=human-confirmed`、`releaseCandidateEligible=false`；不得输出正式发布候选交接。
- 写操作 → 必须 Plan；禁止浏览器点状态。

## 编号与查重

- 优先显式 `ONEOS-xx`；禁止按标题猜编号后静默写。
- 发起前查重：同模块 + 同症状 + 同交付/需求 → 提示更新旧单。
- 写操作一律脚本 `--sn` + 回读；禁止 DOM 点选凑合。
