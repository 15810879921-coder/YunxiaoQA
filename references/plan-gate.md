# Plan 确认清单

凡写云效，Plan 正文至少覆盖下列勾选项（按口令裁剪）。

## 通用头

- [ ] 云效项目名 + `spaceIdentifier`（新建/不确定时已 PJ 点选）
- [ ] 口令类型（开始测试 / 独立发起缺陷 / 从测试用例发起缺陷 / 再次打开 / 批量关闭 / 并入迭代 / 完成测试…）
- [ ] 涉及工作项编号列表
- [ ] **不会做**：不建【开发】/【测试】、不创建迭代、不代开发标已修复/暂不修复

## 发起缺陷 / 从测试用例发起缺陷 / 发起缺陷(非本期)

- [ ] 标题终稿
- [ ] 查重结论：新建 / 复用 `ONEOS-xx`
- [ ] **挂载点选**：【测试】已点选（或口令唯一命中并确认）；需求可选写入描述追溯（见 [anchor-selection.md](anchor-selection.md)）
- [ ] 验证者策略=`当前登录测试用户`；不接受口令覆盖；apply 后必须回报云效解析的姓名+userId和回读值
- [ ] 测试用例路径已提供用例编号/执行记录并声明使用共同`create_bug.py`处理器（独立路径不要求）
- [ ] 负责人姓名 + userId（本期：开发任务来源说明；非本期：口令指定）
- [ ] 关联：【测试】ASSOCIATED（关联项）；需求仅描述追溯（不做 ASSOCIATED API）
- [ ] 优先级（默认中；口令可改）
- [ ] 描述已含：现象、环境、步骤、实际/期望、初步定位

## 再次打开

- [ ] 缺陷编号 + 当前状态确认为 `已修复`
- [ ] 复现说明 / 证据摘要
- [ ] 确认不修改负责人、验证者
- [ ] 若源状态为 `暂不修复`：用户已显式确认坚持打开

## 批量关闭已修复

- [ ] 待关闭编号列表（均为 `已修复`）
- [ ] 已排除复现 / 将再次打开的编号
- [ ] 每条待关闭Bug都分别提供：复测用例、复测执行ID、证据ID/URL、test环境、已部署版本（**小程序**用小程序测试版本标识）、当前验证用户
- [ ] 将逐条调用`transit_bug.py`先写入并回读`oneos.bug-retest/v1`，证据缺一项则该Bug不关闭
- [ ] 关闭后是否检测【测试】可闭环（是/否）

## 并入当期迭代

- [ ] 缺陷编号均为 `已关闭`
- [ ] 目标迭代名称 + sprintId（已存在；非新建）
- [ ] 目标迭代端别与缺陷来源【交付】端侧标签一致（`Web`缺陷不并入小程序迭代，反之同理）；端别无法唯一判定时停下问

## 开始测试

- [ ] 【测试】=`待处理`、需求=`待测试`
- [ ] 【测试】唯一父【交付】、正式关联需求与口令一致
- [ ] 已回读唯一父【交付】及其端别/迭代；缺迭代时先按候选确认流程补绑
- [ ] 不以test部署记录、执行ID或实际版本作为开始测试门禁
- [ ] dry-run显示两侧下一状态均唯一可达

## 完成测试

- [ ] 【测试】=`处理中`、需求=`测试中`
- [ ] 已提供明确的TestHub计划ID并由官方CLI直接回读；计划用例总数>0，未执行/失败/阻塞均为0
- [ ] 用例已由`yunxiao_cli_testhub.py`规划进计划并通过官方CLI回读；不得把用例库中的孤立用例当成计划执行结果
- [ ] 关联缺陷清单；活跃缺陷为0
- [ ] 每条已关闭Bug均有自己的`oneos.bug-retest/v1`复测通过证据；不再与顶层test部署版本做一致性比对
- [ ] 每条`暂不修复`均列出批准人和批准记录ID/URL
- [ ] 将用`yunxiao_cli_test_lifecycle.py complete --test-plan-id <计划ID>`直接回读TestHub和缺陷后推进两侧状态
- [ ] 已明确：不要求test部署记录/执行ID/实际版本、正式测试报告ID/链接、`oneos.qa-evidence/v1`清单或哈希
- [ ] 发布候选交接字段与幂等键
- [ ] 确认不走浏览器点状态；回报两侧`编号 | 标题 | from→to`

## 人工验证通过快捷闭环

- [ ] 用户已针对明确【测试】编号确认“人工验证通过”，不是仅说“继续”或泛化授权
- [ ] 【测试】源状态属于`待处理/处理中/已完成`；正式关联需求属于`待测试/测试中/测试完成`
- [ ] 唯一父【交付】和唯一正式`ASSOCIATED`需求已回读；口令需求与关系一致
- [ ] 关联缺陷无`待确认/处理中/已修复/再次打开`；仅允许`已关闭/暂不修复`
- [ ] 将用`manual-complete --manual-verdict passed`，按需补齐中间态后使【测试】=`已完成`、需求=`测试完成`
- [ ] 已声明该路径跳过TestHub，回执标记`releaseCandidateEligible=false`，不输出发布候选交接
- [ ] 确认不走浏览器点状态；两侧逐步写入并回读

## 父【交付】缺迭代补绑

- [ ] 已从【测试】唯一`PARENT`关系回读父【交付】编号，确认当前`sprint`为空
- [ ] 已按父交付端别过滤已有迭代：Web/PC与小程序不得混挂；已排除归档、锁定和无版本号迭代
- [ ] Plan已列出候选迭代名称、ID、状态和版本排序依据，并声明不会创建迭代
- [ ] 用户已明确确认该候选；apply参数`--confirm-sprint-id`与Plan候选ID完全一致
- [ ] apply后回读父交付编号和`sprint.id/name`，不以请求已发送代替成功

## 需求测试完成（无缺陷捷径）

- [ ] 【测试】=`已完成`且编号与口令一致
- [ ] 验证结论通过（评论或用户确认）
- [ ] 关联缺陷无`待确认/处理中/已修复/再次打开`（无缺陷单=通过）
- [ ] 正式关联需求唯一；当前=`测试中`；目标=`测试完成`
- [ ] 确认不走浏览器点状态；回报`编号 | 标题 | 测试中→测试完成`

## 用户确认用语

接受：`确认` / `执行` / `批准计划` / `按方案执行`。
压缩点选（若 Plan 给了字母表）须先解析回显再执行。
